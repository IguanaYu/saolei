## 0. TL;DR

游戏开发的 8 个标准阶段：

```
Pre-Production → Prototype → Vertical Slice → MVP → Alpha → Beta → Soft Launch → Release
                                                     ↑
                                                  indie 常合并
```

**indie 开发的常见简化路径**：

```
Prototype → MVP → Early Access → Release
   (跳过 Vertical Slice，因为没有发行商)
```

**手游 / 小游戏特有**：

```
... → Closed Beta → Open Beta → Soft Launch → Global Launch
                                    ↑
                              地域限定测留存/变现
```

## 1. 行业标准 8 大阶段

### 1.1 阶段总览

| 阶段 | 英文 | 品质要求 | 工期参考 | 主要目的 |
|---|---|---|---|---|
| 预生产 | Pre-Production | 设计文档 + 概念图 | 1-3 个月 | 立项、技术验证 |
| 原型 | Prototype / First Playable | Greybox（占位美术） | 1-4 周 | 验证核心玩法有趣 |
| 垂直切片 | Vertical Slice | **80% 最终品质** | 2-6 个月 | Pitch 发行商 / 验证整体感觉 |
| 最小可行产品 | MVP | 框架可玩，品质粗糙 | 1-3 个月 | 验证商业可行性 |
| Alpha | Alpha | 功能完整但有 bug | 3-12 个月 | 验证功能闭环 |
| Beta | Beta | 内容完整 | 1-3 个月 | 测试 + 平衡性调整 |
| 软启动 | Soft Launch | 接近上线品质 | 2-8 周 | 地域限定测市场 |
| 正式发布 | Release / Launch | 上线品质 | — | 全球发布 |

> 来源：[The 6 Major Milestones of Video Game Development](https://www.linkedin.com/posts/ifyouwillem_gamedevelopment-gamingindustry-gamedev-activity-7366454773182595074-P-uT)、[软件版本周期 - 维基百科](https://zh.wikipedia.org/zh-cn/软件版本周期)

### 1.2 各阶段详解

#### 1.2.1 Pre-Production（预生产）

**目的**：立项决策、技术验证、设计文档化。

**产出**：
- GDD（游戏设计文档）—— 扫雷挖矿已有 [游戏设计文档.md](../../active/游戏设计文档.md)
- 概念美术
- 技术原型（验证关键玩法可行）
- 工具链选型（Godot 4.6）

**关键决策**：做不做这个游戏？

---

#### 1.2.2 Prototype / First Playable（原型 / 首玩版本）

**目的**：**验证核心玩法有趣**——这是最关键的一步。

**品质要求**：
- 美术：greybox（占位方块 / 简单形状）
- 音效：可有可无
- UI：基础按钮
- **绝对不能**在原型阶段追求美术品质

**关键问题**：
- 核心 Loop 玩起来有趣吗？
- 玩家愿意反复玩吗？
- 5-10 分钟体验后还想继续吗？

**对扫雷挖矿**：v0.2 已完成的 P1-P5（基础扫雷 + opener/marker）就是原型阶段产出。

来源：[游戏设计是怎么一回事 - indienova](https://indienova.com/indie-game-development/how-to-design-a-game/)

---

#### 1.2.3 Vertical Slice（垂直切片）

**目的**：制作一个**完整功能的切片**，包含最终品质的美术、UI、音效、音乐。

**关键定义**：
> "Vertical Slice 之于完整游戏 = 一片蛋糕之于整个蛋糕。"
> —— [The 6 Major Milestones](https://www.linkedin.com/posts/ifyouwillem_gamedevelopment-gamingindustry-gamedev-activity-7366454773182595074-P-uT)

**典型范围**：
- 1-2 个关卡，做到 ~80% 最终品质
- 20 分钟 - 1 小时的游戏体验
- **无占位内容**（无 placeholder）

**主要用途**：
- **AAA / 中型团队**：pitch 发行商拉投资
- **indie**：可选，验证"完整体验"是否成立

**关键决策**：要不要做 Vertical Slice？

| 团队类型 | 建议 |
|---|---|
| 找发行商 | ✅ 必做 |
| 上 Kickstarter | ✅ 必做 |
| indie 自筹 | ⚠️ 可选，看是否需要验证整体感 |
| 个人项目 | ❌ 可跳过，直接 MVP |

来源：[MVP vs Vertical Slice - Unity Discussions](https://discussions.unity.com/t/mvp-vs-vertical-slice/632748)、[Prototypes & Vertical Slice - Rami Ismail](https://ltpf.ramiismail.com/prototypes-and-vertical-slice/)

---

#### 1.2.4 MVP（最小可行产品）

**目的**：**验证商业可行性**——是否值得继续投入。

**关键区别（Vertical Slice vs MVP）**：

| 维度 | Vertical Slice | MVP |
|---|---|---|
| 重点 | **深度 + 品质** | **广度 + 验证** |
| 范围 | 1-2 关做到 80% 品质 | 整体框架可玩 |
| 品质 | 接近最终 | 粗糙可接受 |
| 用途 | Pitch / 验证整体感 | 验证玩法 / 商业 |

**MVP 验证 4 步法**（来源：[独立开发者做小游戏：先验证玩法](https://eastondev.com/blog/zh/posts/dev/20260518-indie-game-mvp-validation/)）：

1. **识别核心 Loop**：玩家反复做的最简行为集合
2. **构建最简原型**：能跑通核心 Loop 即可
3. **真实玩家测试**：找目标用户试玩
4. **决策点判断**：继续 / 调整 / 放弃

**关键决策**：堆系统的时机
- ✅ 核心 Loop 已验证好玩
- ✅ 玩家愿意重复玩
- ❌ 否则：不要堆系统（避免做无用功）

---

#### 1.2.5 Alpha

**目的**：**功能完整**——所有系统就位，可从头玩到尾。

**品质要求**：
- 所有功能就位（可玩）
- 内容可能不全
- Bug 较多
- 美术 / 音效可能仍是占位

**关键特征**：**Feature Complete**（功能完整）

---

#### 1.2.6 Beta

**目的**：**内容完整**——所有内容就位，进入测试与平衡调整。

**品质要求**：
- 所有功能 + 所有内容
- Bug 修复中
- 平衡性调整
- 美术 / 音效基本就位

**类型**：
- Closed Beta（封闭测试，限邀请）
- Open Beta（公开测试，所有玩家）

---

#### 1.2.7 Soft Launch（软启动）

**目的**：**地域限定的小范围真实上线**，测试市场表现。

**典型范围**：
- 选 1-3 个国家 / 地区（如加拿大、澳大利亚、东南亚）
- 2-8 周真实运营
- 收集真实数据：留存、付费、行为漏斗

**核心指标**：
- 次留 / 7 留 / 30 留
- 付费率 / ARPU
- K 因子（社交裂变）

**关键决策**：
- 数据达标 → Global Launch
- 数据未达 → 调整后再测
- 严重未达 → 推迟上线 / 重做

来源：[游戏全球发行 Soft Launch 全攻略](https://zhuanlan.zhihu.com/p/397215868)

---

#### 1.2.8 Release / Global Launch

**目的**：全球 / 全平台正式发布。

**品质要求**：
- 上线品质
- 服务器准备好（如有在线功能）
- 客服 / 运营就位
- 营销推广启动

## 2. 不同团队的阶段裁剪

### 2.1 AAA 团队（完整流程）

```
Pre-Production → Prototype → Vertical Slice → Alpha → Beta → Soft Launch → Release
                                                     ↑
                                                发行的标配
```

### 2.2 Indie 团队（不找发行商）

```
Prototype → MVP → Early Access → Release
   ↑                              ↑
跳过 Vertical Slice         提前上线收反馈
```

来源：[Moving from AAA to Indie Dev - Reddit](https://www.reddit.com/r/gamedev/comments/5642qs/moving_from_aaa_to_indie_dev_is_the_vertical/)

### 2.3 手游 / 小游戏（重点 Soft Launch）

```
Prototype → MVP → Alpha → Beta → Soft Launch → Global Launch
                                       ↑
                                  关键阶段，1-3 个月
```

### 2.4 个人项目（极简）

```
Prototype → MVP → Release
   ↑
直接验证 + 上线
```

## 3. 关键决策点

### 3.1 阶段间决策（强制 gate）

每个阶段完成后**必须停下来**评估：

| 评估项 | 通过标准 |
|---|---|
| **核心假设是否验证** | 该阶段的核心问题被回答 |
| **数据 / 反馈是否达标** | 定量指标达到目标值 |
| **是否有意外发现** | 玩家行为符合预期 |
| **技术债 / 设计债** | 可控 |
| **下一步是否清晰** | 知道下阶段做什么 |

### 3.2 调整 / 回退机制

| 情况 | 处理 |
|---|---|
| 数据接近达标 | 微调后进下阶段 |
| 数据明显未达 | 找原因，本阶段重做 |
| 发现根本性问题 | 回退到上一个阶段 |
| 发现方向错误 | 回到 Prototype 重做 |

### 3.3 跳过 / 合并阶段的判断

| 阶段 | 跳过条件 |
|---|---|
| Vertical Slice | 不找发行商 / 不需要验证整体感 |
| Closed Beta | indie / 个人项目可合并到 Soft Launch |
| Soft Launch | 个人项目 / 不重视数据可跳过 |
| Early Access | 仅 indie 适合，AAA 不用 |

## 4. 工期参考（行业标准）

### 4.1 indie 项目典型工期

| 阶段 | 工期 |
|---|---|
| Prototype | 1-4 周 |
| MVP | 1-3 个月 |
| Alpha | 3-9 个月 |
| Beta | 1-3 个月 |
| Soft Launch | 2-8 周 |
| **总计** | **6-18 个月** |

### 4.2 小游戏 / 手游典型工期

| 阶段 | 工期 |
|---|---|
| Prototype | 1-2 周 |
| MVP | 2-4 周 |
| Alpha | 1-3 个月 |
| Beta | 2-4 周 |
| Soft Launch | 2-4 周 |
| **总计** | **3-6 个月** |

> 来源：[独立游戏单人开发完整路线图](https://plumephp.com/solo-indie-roadmap-scale-guide/)

### 4.3 工期估算原则

| 原则 | 说明 |
|---|---|
| **2x 法则** | 实际工期 = 预估 × 2 |
| **渐进明细** | 近期 sprint 详细，远期粗略 |
| **不要全功能** | 每阶段只做必要功能 |
| **保留 buffer** | 每阶段留 20% 缓冲时间 |

## 5. 敏捷开发与里程碑的结合

### 5.1 Sprint + Milestone 双轨

```
里程碑（宏观）：  M1 ───────────── M2 ───────────── M3
                  │                │                │
Sprint（微观）：  S1 S2 S3 S4      S5 S6 S7 S8      S9 S10 S11 S12
                  │                │                │
Daily（执行）：   ───────────────────────────────────────→
```

- **里程碑**：宏观目标，定义"做到什么程度"
- **Sprint**（2-4 周）：迭代周期，定义"做什么"
- **Daily**：日常执行

### 5.2 GDC Bungie Epic Sync 案例

Bungie 在《命运》系列中用 Epic Sync 实现大规模敏捷：
- 多个团队并行开发
- Epic（史诗）级需求跨团队同步
- Sprint 节奏统一

来源：[学习记录：GDC Bungie 规模化敏捷实践](https://zhuanlan.zhihu.com/p/111397637)

### 5.3 渐进明细原则

> 当前 Sprint 详细，未来 1-2 个 Sprint 较详细，更远的粗粒度管理。

来源：[华为云：敏捷需求管理](https://support.huaweicloud.com/bestpractice-projectman/projectman_practice_1007.html)

**应用**：
- M1 详细到任务级（每天做什么）
- M2 详细到功能级（做什么功能）
- M3+ 只列范围（大致做什么）

## 6. 对扫雷挖矿的里程碑规划建议

### 6.1 项目现状评估

**已完成（v0.2）**：
- ✓ Pre-Production（GDD 完成）
- ✓ 部分 Prototype（核心扫雷 + opener/marker）
- ✓ 部分功能（detector/miner/塔/无人机）

**未完成**：
- ✗ 完整 Prototype 验证（核心 Loop 是否真的"打不过→升级→碾压"）
- ✗ MVP（核心循环 + 局外成长能跑通）
- ✗ Alpha（关卡章节系统等完整功能）
- ✗ Beta（内容完整 + 调优）
- ✗ Soft Launch

### 6.2 推荐路径

**Indie + 个人项目 + 已有部分基础** 的最佳路径：

```
当前位置
   │
   ▼
[M1 Prototype]        验证"打不过→升级→碾压"核心循环
   │                  (3-5 关 + 1-3 升级链)
   ▼
[M2 Vertical Slice]   验证完整章节体感
   │                  (1 章节 10 关，含品质打磨)
   ▼
[M3 Alpha]            全功能 + 全章节
   │                  (6 章节 60 关 + 装备 + 多角色)
   ▼
[M4 Beta]             调优 + 商业化
   │                  (社交玩法 + 月卡 + 平衡)
   ▼
[M5 Soft Launch]      地域限定测试
   │
   ▼
[Release]             正式上线
```

### 6.3 关键决策

| 决策点 | 建议 |
|---|---|
| **是否跳过 M2 Vertical Slice？** | 不跳——验证完整体感对扫雷挖矿重要 |
| **是否合并 M3 + M4？** | 不合并——内容量大，分开降低风险 |
| **是否做 M5 Soft Launch？** | 看 M4 完成情况——如果数据很好可跳过 |
| **每个 MS 多长？** | 见 [里程碑路线图.md](../../active/里程碑路线图.md) |
