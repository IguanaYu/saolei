# 可行性调研:竖长地图 / 任意形状地图 / 多格障碍(化石)

> 生成于 2026-10-04。触发:三个设想——(A) 超长竖条地图,玩家从底部往上扫雷推进;(B) 任意 DIY 形状地图(含 L 形、镂空);(C) 多格障碍物(如"化石"占 2×2,挡住格子)。本文为只读调研结论,未动任何代码。
> 证据标注:**[代码]** = 本项目源码核实(附行号);**[A]** = 一手网页抓取;**[B]** = 模型知识/搜索回退内容,当日未联网核实(搜索配额耗尽,10-13 重置后可补核)。

## 0. 结论

| 方向 | 可行性 | 工程量 | 一句话 |
|---|---|---|---|
| C 化石(2×2 障碍) | ✅ 可行 | 小 | 单格状态位范式现成(is_locked / is_on_fire / path_blockers),主要坑在 Solver/和弦计数口径与胜利判定分母 |
| B 任意形状(L 形/镂空) | ✅ 可行 | 中 | 地基意外地好:棋盘本来就是 `Dictionary{Vector2i→Cell}`,运行时边界判断全靠 `cells.has()`,天然形状无关;卡点集中在 4 处矩形假设 |
| A 竖长地图(20×200) | ✅ 可行,但工程最大 | 大 | 全项目零 Camera2D、零滚动、零缩放,"居中即全图"的假设遍布 main/cave_env/侧栏,相当于从零新建视口层;另有节点量与全盘扫描的性能重估,以及一局节奏的重新设计 |

推荐落地顺序 **C → B → A**:C 最小且独立;B 顺手修一个现存 bug(_in_bounds 轴反);A 依赖 B 的"参数化格子创建"作为前置。A 不只是技术问题——4000 格 vs 现有 256 格,单局时长与经济模型需要另立节奏设计(可走 game-pacing 流程)。

## 1. 现有架构关键事实 [代码]

1. **存储形状无关**:`Grid.cells: Dictionary{Vector2i → Cell}`(`scripts/grid.gd:14`),非 Array2D。任意形状=字典里少几个键,下游大部分代码无感。
2. **渲染=每格实例化节点**:每格一个 `Cell(Area2D)` 场景(`scripts/grid.gd:16, 211-216`),岩壁/洞底是每格 AtlasTexture 切块(`scripts/cell.gd:153-194`)。全项目**无 TileMap/TileMapLayer、无 Camera2D、无缩放/滚动**。
3. **布局=居中即全图**:`_center_grid()` 把整盘摆进 `_play_area` 中心(`scripts/grid.gd:194-200`);play area = 视口 − HUD 顶栏 − 底部商店(`scripts/main.gd:433-442`)。窗口 1024×768 固定。
4. **布雷=固定数量制**:候选格洗牌取前 N(`scripts/map_generator.gd:14-41, 47-77`),候选枚举是矩形双循环(`:16-17, 51-52, 66-67`)。首击安全=首基地 ±(1+局外扩区) 方框内排除(`scripts/grid.gd:277-286`)。
5. **邻居/洪水/Solver/寻路全靠 `cells.has()` 截断**:`get_neighbors`(grid.gd:452)、`_flood_open`(grid.gd:665)、敌虫寻路(enemy.gd/pathfinding.gd)、Solver(solver.gd:17)——无一处 `x+1 < width` 式矩形判断。**这是 B 的最大利好。**
6. **已有阻挡格全是 Cell 状态位**(单格粒度,非独立节点):`is_locked`(锁,谁都不能开,grid.gd:683-690 / guard_robot.gd:144-158)、`is_webbed`、`is_slimed`、`is_on_fire`+`path_blockers` 计数(cell.gd:9-28;`is_walkable` 要求 `is_opened and path_blockers==0`,grid.gd:551-556)。**不存在任何多格占位概念。**
7. **寻路=BFS 4 向**(`scripts/pathfinding.gd:17-48`),机器人每 tick 全盘重扫 Solver + 全盘 BFS(robot.gd:111;现有性能预算按 16×16=256 格论证,docs/active/实现设计文档_v0.2.md:548)。
8. **胜负=揭开所有非雷格**:`count_safe_remaining()==0` → `all_safe_opened`(grid.gd:480-482, 569-574),遍历 `cells.values()`,形状无关;但**无连通性/可达性校验**——安全格被围死则永远差格。
9. **存档零耦合**:user://save_data.json 只存局外数据(save_system.gd:93-107),不存棋盘状态与尺寸。三个方向均零存档迁移成本。
10. **关卡参数来自代码常量**:`LevelDatabase.CELLS := 16*16` 推算雷数(level_database.gd:5, 266-268);每日挑战已用非方形盘 rows 10–13 / cols 12–18(daily_challenge.gd:96-114)——注意见 §6 现存 bug。

## 2. 方向 A:超长竖条地图(如 20 宽 × 200 高)

### 2.1 硬卡点 [代码]

1. **视口层从零新建**:需加 Camera2D(前沿跟随或滚轮/边缘滚动)+ 缩放;`_center_grid` 的"整盘居中"改为"水平居中 + 垂直由相机控制",`limit_*` 钳到盘界。
2. **输入坐标换算**:`main._input` 直接把 `event.position` 屏幕坐标当世界坐标传给 `grid.world_to_coord`(main.gd:766-768, 903-908)。加相机后必须改 `get_global_mouse_position()`/canvas 变换。Cell 自身的 Area2D input_event 不受影响。
3. **背景与边框进世界层**:CaveEnv 全屏背景是全矩形锚点 Control + 矩形岩框(cave_env.gd:77-106);GridLines 同为矩形(grid.gd:21-32)。滚动时需搬进世界坐标或改 ParallaxBackground。
4. **侧栏冲突**:左右事件日志侧栏是固定屏幕坐标(Main.tscn:69-82,各占 ~260px),之间自由区约 504px;20 列×28px=560px 会穿进侧栏底下——需收窄侧栏、棋盘贴边,或减列宽/列数(18 列=504px 正好)。
5. **关卡数据**:`LevelDatabase.CELLS=16*16` 常量推雷数,新关需显式 grid_size/mine_count;FixedBoards 全是 16×16 内坐标,竖图关走参数化的 `apply_random_board`(grid.gd:337-379,无尺寸假设)或新烘焙数据;Boss 关锚点/触手/落弹全按矩形盘边(boss_manager.gd:101-109, 216-233, 303-344),竖图关直接不配 Boss 即可绕过。

### 2.2 性能预算重估 [代码]+[B]

- 20×200=4000 格 ≈ 现有 15.6 倍;每格子树约 7 节点 → ~2.8 万节点(现 ~1800)。Godot 4 扛得住静态节点量,但 4000 个 Area2D 输入拾取与每 tick 全盘 BFS/Solver 扫描会叠加。
- 粗估(线性外推,现预算 20 台 <1ms @256 格):全盘 BFS+Solver 单次 ~15ms。机器人 tick 0.3s 分散触发时大概率可接受,但 20 台齐空闲时会尖峰——预案:寻路/Solver 限定在"前沿窗口"(最新基地 ±N 行)内扫描,或脏标记缓存。
- 渲染层若再不够,迁 TileMapLayer(分块+自动剔除)[B] 或**惰性行实例化**:玩法本身就是"从下往上逐步推进",前沿以上 N 行之外根本不用实例化——这套惰性窗口天然支持"无限模式"延伸。
- 建议先做 20×60 中图实测帧率,再决定 200 行还是惰性方案。

### 2.3 设计层问题(非技术卡点)

- **一局时长**:256 格配的是 90s 生存/清盘节奏;4000 格直接套 CLEAR_ALL_SAFE 会让单局膨胀一个数量级。候选:新增 `REACH_ROW`(抵达第 N 行)目标类型;每 N 行一个"阶段门/检查点"(配合基地=存档点的感觉);或无限模式+深度里程碑。数值需另立节奏设计文档。
- **推进循环正好契合现有机制**:出生=最新基地旁 BFS 最近格(main.gd:951-968)→ 竖图里"往上建基地=爬塔",基地链与推进方向天然自洽;探测 3×3、保安射程(切比雪夫≤4)都是形状无关的方形范围,竖图无影响。
- 竖向推进的镜头语言有成熟先例(Mr. Driller / Dome Keeper / SteamWorld Dig:镜头跟随挖掘前沿,深度=进度)[B]。

## 3. 方向 B:任意形状地图(L 形/镂空)

### 3.1 卡点(集中在 4 处矩形假设)[代码]

1. **格子创建**:`init_empty_grid` 的 `for y in rows: for x in cols` 双循环(grid.gd:204-235)——**B 的核心改动点,改为按形状坐标集/掩码生成,改动面极小,下游全兼容**。
2. **布雷候选枚举**:map_generator 三处双循环(§1.4)。过渡方案:把盘外/洞格全塞进现成的 `exclude_coords` 机制;根治=generate 改接受坐标集。
3. **盘边取点 4 处会取到洞里**:巢 `_random_edge_coord` 用 `randi_range(1, cols-2)` 算坐标且不校验存在(enemy_manager.gd:149-159);Boss 锚点/爬角(boss_manager.gd:101-109, 136-138)。统一加 `cells.has()` 校验重取即可。
4. **`main._in_bounds` 轴向写反**(main.gd:971-972,详见 §6):任意形状下应直接改为 `grid.cells.has(coord)`。

### 3.2 视觉

- CaveEnv 矩形岩框 + GridLines 矩形网格线按形状包围盒或边缘检测重画(仅美观)。
- Cell 已有"无邻居侧=洞口描边"的边缘检测(cell.gd:257-263)——本身就是形状感知的雏形,L 形内缘/洞缘会自然描边,效果可接受,细节再调。
- `_center_grid` 用包围盒居中,L 形视觉略偏心(美观问题,可按实际占格重心居中)。

### 3.3 形状数据格式建议

- LevelData 增加 `shape`:行字符串掩码(如 `"1111000/1111000/0111000"` 一眼可读,配 .gd 常量或 JSON)或坐标集;`FixedBoards` 的坐标列表+`cells.has` 校验格式(grid.gd:305-331)**天然已支持任意形状**,手工异形关几乎零成本。
- 若做玩家向 DIY 编辑器(非本调研主设想的"开发者手工关"),另需:连通性校验(从首基地 BFS 可达所有格)、可胜利性校验(无被围死安全格)、雷密度上下限——都是一次性小工具函数,但不建议首期做。

## 4. 方向 C:多格障碍(化石 2×2)

### 4.1 表示方案(推荐前者)

- **方案一(贴合现状)**:4 个格子共享同一 `obstacle_id` 的 Cell 状态位(仿 `is_locked`),记录 2×2 原点归属;挖掘拦截仿锁在 `Cell.open()/toggle_flag()` 顶部拒绝(cell.gd:312-318, 344-346)。
- 方案二:独立 Obstacle 节点占位并给 4 格各 +1 `path_blockers`(仿火)——好处是天然挡敌虫/机器人,坏处是引入第二套棋盘实体。
- 点击分流复用现有 obstacle 分流(grid.gd:697-743)。**设计定调(2026-10-04 用户确认):化石=纯难度件,永久占位、不可清除**。现有分流恰好零成本支持该语义:`clear_cell_obstacle` 对化石返回空 → `has_obstacle` 分支直接 return、**不消耗玩家 CD**(grid.gd:706-711 的 kind=="" 路径已核实),点化石=无效操作(可后补抖动反馈)。比"可清除收藏品"方案更省——少一整套清除交互与奖励发放。

### 4.2 数字语义:两种流派,推荐透明口径

- **透明口径(推荐)**:数字照常数 8 邻雷,化石格只是"可见的、不可开的安全占位"。MapGenerator 数字计算**零改动**;Tametsi 的缺格即此语义(数字只数存在格中的雷)[A/B]。
- 阻断口径:化石邻格数字减小(化石当"已排除格")——需重算 adjacent_mines,玩家推理表述更绕,不推荐。
- **关键代码坑(无论哪种口径)**:chord 与 Solver 把 `is_vein/is_collapsed/is_confirmed_mine` 等价旗计入雷数(grid.gd:522-525, 769-779;solver.gd:24-29),化石必须在两处显式排除,否则污染推理;参照锁格"参与计数但跳过动作生成"的先例(solver.gd:26-29, 34-36, 44-46)。

### 4.3 化石会"挡住数字"吗?会不会影响玩家开格(2026-10-04 补充分析)

结论:**不会挡住任何数字,也不会卡住任何合法开格**;化石对信息的唯一影响是"少了一个本可显示数字的格子",这本身就是难度来源。分层说明:

1. **数字永远不会被化石遮挡**:数字只存在于**已开格**上,化石格永远不可开、永远不渲染数字;化石邻格的数字照常显示,透明口径下数值也不因化石存在而改变(照常数 8 邻雷,化石格内无雷)。玩家眼中的化石="已知安全、已知不可开"的占位格。
2. **"本可提供的数字没了"=难度而非死局**:化石格自己那个数字确实不存在了,等价于 Tametsi 的缺格——局部信息变少,推理变难,但不会产生逻辑矛盾;不会出现"某个格子因缺这条数字而永远推不出来还不能开"的死锁(缺格盘在无猜拼图里是成熟形态)。
3. **对开格操作零阻碍(已核实)**:玩家点击开格无射程/可达性限制——`_on_cell_left_clicked` 直接 `open_cell(cell.coord, "player")`(grid.gd:697-723),化石只拦"它自己占的那 4 格",不拦任何别的格子。需要受控处理的三处均有锁格先例:① 和弦双击连开时跳过化石格;② 洪水连开在化石处截断(免费瀑布变小=设计意图);③ Solver 不把化石格当可开/可标候选。
4. **胜利不卡死**:化石 4 格从 `count_safe_remaining/count_safe_total` 分母剔除后,CLEAR_ALL_SAFE 不受影响(§4.4)。
5. **唯一真边缘情况——化石围死的"口袋"**:若化石(叠加盘边/互相拼接)把一小块可开格完全围住:玩家**仍可手点开**这些格子(第 3 条,无射程限制),胜利不卡;但机器人 BFS 永远找不到与口袋格相邻的落脚格(8 邻全是不可走格),只能玩家手动。属可接受的"玩家高光时刻",但要防机器人反复选它当目标而空转——两个缓解任选:① 机器人/Solver 目标选择加"存在可达落脚格"过滤;② 生成时轻量连通性校验(化石+盘外当墙,从首基地区 BFS,所有可开格可达才放行),彻底杜绝极端盘面。

### 4.4 其余接入点 [代码]

- 布雷:化石先放,布雷 exclude 之(generate_excluding 现成)。
- 敌虫:`find_path_free_step` 只查 `cells.has`(pathfinding.gd:96),虫会穿化石——加阻挡判定。
- Boss 抛锁候选(boss_manager.gd:263-268)、EnemyManager 预设 hazard 候选(enemy_manager.gd:163-191)过滤化石格。
- **胜负分母**:`count_safe_remaining/count_safe_total`(grid.gd:569-583)必须把化石格剔除,否则 CLEAR_ALL_SAFE 永远差格(§1.8 无可达性校验)。
- 视觉:单格障碍贴片范式现成(`_setup_obstacle_mark`+OVERLAY_*,cell.gd:72-79, 121-138);2×2 整图拆 4 块 overlay 或把大精灵挂 EffectsLayer(z 序 grid.gd:83-92)。

## 6. 调研中发现的现存 bug(与决策无关,建议尽快修)

1. **`main._in_bounds` 轴向写反**(`scripts/main.gd:971-972`):判断写作 `coord.x < grid.rows and coord.y < grid.cols`,但格子创建是 `for y in rows: for x in cols`(x 对应 cols)。方形盘无症状;**每日挑战已用非方形盘(rows 10-13 / cols 12-18),右侧 x≥rows 的列放不了首基地——这是线上可复现的活 bug**。任意形状下应整体改为 `grid.cells.has(coord)`。
2. **`level1_director.gd:35,49` board_size 轴反**:`Vector2(rows*cell, cols*cell)` 宽高对调,方形盘无症状,非方形关引导框会变形。

### 8.1 两关现状 [代码]

- **L3 积分关**:16×16 / 40 雷 / 固定盘(base=(3,5) 预置,preopen 101 格,`FixedBoards.L3`),REACH_SCORE 300 @150s,机制=升级+基地+局外成长。烘焙验收含**节奏数字**(过线时 29 旗+54 开格、停摆总分 395,tmp/level3_board_finder.py + 第三关设计文档 §7)。
- **L4 除虫关**:16×16 / 40 雷 / 固定盘(玩家自放基地 fixed_base=(-1,-1),preopen 57 格,`FixedBoards.L4`),CLEAR_ALL_SAFE **打折线 160/216≈77%**(盲测反馈调出,level_database.gd:177-181),机制=探测+保安+虫害(预置网×3、虫巢裂缝)。
- 关键先例事实:`count_safe_remaining/count_safe_total` **只排除雷、不排除锁格**(grid.gd:569-583)——L4 靠打折线而非分母剔除消化锁格;化石落地时必须真正从分母剔除(否则进度条永远差 4 格)。

### 8.2 结论

1. **"给 L3/L4 加化石" = 引擎 C 切片(§4,全关卡生效) + 盘面数据一行**(fixed_boards.gd 对应关加 `"fossils": [Vector2i(x,y)]` 键)。数据侧成本≈0;成本全在引擎侧,且引擎做完后 L1-L5+每日挑战自动全部获得化石能力 → **回归面是全关卡,不只目标关**。
2. **推荐正式落位 L4**,理由:① 教学课程匹配——L4 本就是障碍关(在教"锁/网=可清障碍"),化石="不可清除的永久地形"是同一堂课的自然对比("这个清不掉,绕过去");② 胜利线余量足——160/216=77%,吃掉 4 格后 160/212≈75.5%,**线不用重调**;③ L3 是节奏调校盘,300 线的过线节奏(29旗+54开格)是烘焙验收内容,加化石要重验节奏数字。
3. **L3 更好的用途是引擎白盒验证场**:无虫、无 Boss、预置基地(少"自放基地落化石格"分支)、交互面最小,验证最干净;验证完可留在 L3(对外说成"变难的加分关")或撤掉。
4. **L4 落位的硬前提**(L3 无此问题):① 敌虫阻挡必须先修——`find_path_free_step` 只查 `cells.has`,虫会当面穿过化石,恰好 L4 是虫害展示关,穿模=教学反效果;② 虫巢裂缝/hazard 预置候选要过滤化石格;③ 玩家自放基地要拒绝化石格。
5. 对两关数值的实际扰动:L3 化石吃 4 个开格分,总分上限 395→391,对 300 线可忽略;L4 打折线绝对值 160 不变,仅 HUD 分母 216→212(设计文档"约 77%"文案要同步成 75.5%)。

### 8.3 落位约束清单(选坐标时逐条过)

1. **4 格均非雷**——若盖到雷,该雷消失→总雷数 40 变少→周边数字全变→整盘烘焙验收作废,必须重跑 finder 脚本重选盘;
2. 不在 preopen 内(已开格);L3 另避开 base=(3,5)±安全区;
3. 不与盘边/锁群/另一化石围出机器人不可达口袋(§4.3 第 5 条);
4. 候选区:L3 右下未开区(preopen 集中左上)、L4 西侧未开区(preopen 集中中右)——挡机器人直路=加难度,但别堵探测要道;
5. 素材:2×2=56×56px 化石贴图一张(4 块 quarter overlay,或 EffectsLayer 整图);
6. 收尾三件套:重跑 levelN_board_finder 验收、全关卡回归(引擎改动波及所有关)、L4 设计文档与关卡内文案同步(216→212、77%→75.5%)。
