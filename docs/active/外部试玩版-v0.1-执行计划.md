# 扫雷挖矿 · 外部试玩版 v0.1 执行计划

> 记录日期：2026-09-27  
> 状态：六步顺序已确认；每一步的具体取舍在执行前逐项讨论。  
> 当前步骤：第 1 步「锁定试玩范围」。

**目标玩家（已确认）**：有一定扫雷经验、熟悉数字推理和标雷的玩家。扫雷是吸引他们进入游戏的题材与入门技能；局内主要玩法是投资和布置机器人，让机器人自动开安全格、标雷，玩家在必要时用自己的扫雷判断帮助机器人继续工作。外测招募与教学设计均以这类玩家为基准。

**核心决策（已确认）**：正确投资是主要乐趣。玩家根据当前瓶颈、剩余时间和资金，决定何时买哪种机器人、是否升级、何时增建基地以及放在哪里；机器人自行执行任务。投资的主要目的在于让机器人扫雷更快、获得更多积分；购买只扣局内资金，不扣通关积分。布局影响作业效率。试玩版不以划分作业区域、逐个设定任务优先级等微观调度为主。

**玩法侧重（待外测验证的设计假设）**：机器人扫雷是主玩法，采矿提供附加得分和可继续投资的资金。检测与矿工仍在第一关出现，让玩家看见完整系统，但不把反复运输矿石当成关卡的主要目标。面向扫雷玩家时，以棋盘上的开格、标雷和机器人协作为通关主线；通过盲玩验证这种侧重是否比采矿主导更有吸引力。

**单局节奏（已确认）**：90 秒是挖矿局的结束时间。通关目标提前达到时，按剩余时间增加结算分数；花更久达标，时间加分更低。90 秒到点立即退出并正常结算、保留当局获得的收益，显示“本次挖矿结束”，不显示“失败”或“超时失败”。若到点仍未达目标，本关可以重玩，下一关暂不解锁；达标后才解锁。90 秒不能用完不是问题，剩余时间正是追高分的空间。**待细化**：扫雷进度如何定义通关目标、机器人与玩家的操作如何计分、采矿附加分和时间加分的权重，以及局内收益换成局外奖励的比例。

## 目标与验收边界

先交付一个可供目标玩家独立游玩的 Windows 封闭试玩包。玩家不需要安装 Godot；解压后能启动，第一关就体验「扫雷判断 → 亲手购买开格/标雷机器人 → 看机器人推进棋盘 → 检测与采矿获得附加分 → 结算」，随后在关卡中学习再投资与布局，并能反馈遇到的问题。建议以 5 关、约 15–25 分钟作为第一轮内容目标，实际时长由盲玩结果校准。

封闭试玩通过后，再推进公开 Demo、商店页与宣传素材。公开 Demo 的质量门槛高于第一轮外测包；Steam 官方也分别提供受控 Playtest 与公开 Demo 的发布方式。

## 已确认缺口

### 可玩内容

- 当前检测机器人在第 2 章末解锁，矿工在第 3 章末解锁；第一章还明确禁用这两类机器人。首关要让玩家亲手购买机器人并看到采矿得分，必须重设试玩章节的开放规则；现有解锁与关卡数据见 [`level_database.gd`](../../scripts/data/level_database.gd) 和 [`level_system.gd`](../../scripts/autoload/level_system.gd)。
- 首关采用 16×16 棋盘、90 秒时限。它是否适合目标玩家尚无真人计时数据；这是待验证的平衡风险，不视为已证实的不可通关问题。程序化盘面的推理质量与被迫猜雷比例也待测量，以免干扰运营节奏。
- 新手引导目前只覆盖放基地、购买基础机器人等操作，没有带玩家完成检测矿脉和采矿运输；对目标玩家应集中解释新增系统，让他们尽快做第一次购买决策并看到积分增长。
- 当前机器人自主寻找最近的确定目标或矿脉，矿工自动回最近基地；玩家已有购买顺序、机器人配比、放置位置、基地布局及速度/折扣升级等选择。尚未验证这些选择在短局内是否足够有分量、玩家能否看出积分增长速度与运输瓶颈；试玩版的核心决策深度需在第 1 步定范围。
- 开格和标雷机器人目前只使用两条局部确定性规则（数字周围的雷已标满则开格、剩余未开格数等于剩余雷数则标雷），且逐步移动、按间隔行动。更复杂的可推理局面可能使机器人闲置；若机器人扫雷是主玩法，需验证首关及后续关卡中机器人实际完成的开格/标雷比例，并据此调整盘面、求解能力或机器人速度。相关逻辑见 [`solver.gd`](../../scripts/solver.gd) 和 [`robot.gd`](../../scripts/robot.gd)。
- 首关目前起始资金为 150；按现价购买首座基地、开格、标雷、检测和矿工共需 320。检测机器人只能处理已经插旗的格子，矿工只能采已形成的矿脉。因此首关需安排可识别的雷位、可到达的作业路径和足够的启动资金，让玩家亲手购买，并在 90 秒内看到机器人扫雷与一次采矿附加分；不预置一套替玩家购买的机器人。首关是否必须买齐四种机器人，需在内容表中定，避免把教学变成固定购物清单。
- 现有每章的 5 关目标依次为清空安全格、插旗、积分、清空安全格和存活计时；现有起始资金、递增价格与 90 秒时限是否能形成有意义的机器人扫雷选择尚未实测。试玩关卡应以棋盘推进为通关主线、采矿为附加得分；还需验证玩家手动扫雷是否能轻易替代机器人。
- 现有倒计时归零会触发 `timeout`，关卡结算页显示“时间到”、跳过收益发放，并在统计中中断连胜；这与“本次挖矿结束并结算收益”不符。星数只在结算时按“剩余时间至少一半”加 1 星，剩余秒数不计入分数。当前买机器人、基地和升级只扣 `money`，不扣 `score`；矿工卸货同时加资金和积分，这一点符合已确认的规则。现有开格与标雷不区分玩家或机器人，矿工每次卸货也直接加分；需明确扫雷通关进度、采矿附加分和时间奖励的关系，防止单靠采矿分数或单靠玩家点击就绕开机器人扫雷主线；相关逻辑见 [`main.gd`](../../scripts/main.gd)、[`game_state.gd`](../../scripts/autoload/game_state.gd)、[`miner_robot.gd`](../../scripts/robots/miner_robot.gd) 和 [`results_panel.gd`](../../scripts/ui/results_panel.gd)。

### 已证实的规则与流程问题

- 商店显示 `DEBUG: +200 钱`，可反复领取局内金币；[`Shop.tscn`](../../scenes/ui/Shop.tscn)、[`shop.gd`](../../scripts/ui/shop.gd)。
- 同一颗雷取消旗子后再次插旗，会再次获得钱、积分和标雷目标计数；[`grid.gd`](../../scripts/grid.gd)、[`main.gd`](../../scripts/main.gd)。
- 引导延迟 0.5 秒出现；玩家若先放基地，事件被丢弃，引导卡在第一步。引导显示期间局内计时仍继续；[`main.gd`](../../scripts/main.gd)、[`tutorial_guide.gd`](../../scripts/ui/tutorial_guide.gd)。
- 每日挑战宣称“全球同图”，但日期种子未进入地雷生成，雷位仍随机；[`daily_challenge.gd`](../../scripts/ui/daily_challenge.gd)、[`map_generator.gd`](../../scripts/map_generator.gd)。

### 对外交付

- 项目没有 `export_presets.cfg`，当前机器缺匹配的 Windows 导出模板，尚无可重复构建的发行包。
- [`grid.gd`](../../scripts/grid.gd) 预加载 `scenes/Cell.tscn`，实际文件为 `scenes/cell.tscn`；需统一大小写并在正式包验证。
- `tmp/` 含大量过程素材与测试场景；按主场景依赖导出则可能漏掉动态路径加载的贴图。导出规则需同时解决这两点，并检查包内文件。
- 音频设置仍是占位；缺发行版操作说明、版本号、反馈入口及随包授权声明。字体许可文本目前留在未跟踪的 `tmp/fpx/`，需要建立可交付的素材来源与授权清单。
- 工作区中有未提交的 `scripts/cell.gd` 与多套美术素材。发行包必须对应一个确定的 Git 提交，避免无法重建。

## 六步执行顺序

### 第 1 步：锁定试玩范围与版本基线

**要做**

1. 以已有扫雷经验的玩家为第一轮受众，写清「扫雷加机器人挖矿」的一句话卖点，确定 Windows 交付方式、预期游玩时长，以及 5 关试玩章节的边界。
2. **第一关即展示亲手购买机器人、自动开格/标雷，以及检测和采矿附加分（已确认）**。为此设计首关的保证可解局面、启动资金、引导提示与扫雷通关目标；后续 4 关逐步考察机器人配比、再投资、基地布局和综合运营。确定每关开放的模块、投资考题、90 秒内的目标及结算后解锁。
3. 按“机器人扫雷为主、采矿得分为辅”的假设设计试玩版计分：购买设备只扣资金，不扣积分；开安全格和正确标雷推进关卡，矿工运输提供额外分数和再投资资金，提前达标按剩余时间加分。确定玩家与机器人操作如何计分、附加分是否参与达标、机器人闲置时玩家怎样介入，以及玩家如何看见扫雷进度与积分增速。保留多条可行投资路线，避免靠隐藏数值猜出唯一正确答案；讨论被迫猜雷是否允许，以免猜测决定运营成败。
4. 从现有美术中选定一套可读、统一的基础主题；盘点未提交代码和素材，整理出可重建的基线提交。
5. 标出试玩版中要呈现的菜单和功能；每日挑战、签到、充能塔等入口在进入发行候选包前逐项决定是否开放。

**完成标准**：有一份可执行的 5 关内容表、功能范围表和对应的 Git 基线。  
**下一次优先讨论**：确定“扫雷推进关卡、采矿加结算分”是否作为首轮外测假设；再细化机器人和玩家开格/标雷的计分方式，随后安排首关启动资金与第 2–5 关投资考题。分值和目标值以试玩结果校准。

### 第 2 步：建立内部 Windows 构建

**要做**

1. 安装与 Godot 4.6.1 匹配的 Windows 导出模板，创建并提交导出预设。
2. 排除 `tmp/` 等过程资源，同时确保动态加载的主题贴图进入发行包；统一资源路径大小写。
3. 从第 1 步的基线生成内部 Release 包，在未安装 Godot 的 Windows 环境启动并检查素材与字体。

**完成标准**：同一提交可重复生成一个能进入主菜单和棋盘的 Windows 包；记录构建命令、版本与包内资源清单。

### 第 3 步：修复外测前的规则与流程阻塞

**要做**

1. 移除正式包中的加钱按钮和 F5 调试换肤入口；修复重复插旗刷奖励与目标计数。
2. 修复引导事件时序，并让阅读引导不消耗可操作时间。
3. 每日挑战要么保证同一天同盘面，要么在本轮试玩版中收起相关入口与承诺。
4. 做针对性回归：放基地、开格/标雷、胜利/失败/超时、暂停/重开/放弃、结算奖励、退出重进读档。

**完成标准**：上述确定问题均有可复现的修复验证；没有已知的无限刷资源或流程卡死。

### 第 4 步：完成 5 关内容和首次游玩引导

**要做**

1. 第一关就开放开格、标雷、检测与矿工，让玩家亲手购买并看到机器人扫雷带动棋盘进度、采矿带来附加分；第二至第五关再增加机器人配比、再投资、基地布局和综合运营的难度。关卡目标优先围绕扫雷进度设计，资金支出不扣积分；每关应让不同投资产生可感知的推进速度差异。
2. 教程用少量手动扫雷让玩家理解机器人替他们做什么，随后重点用实际操作介绍基地、机器人、检测、矿脉采集、卸货与再投资；说明新增操作并允许跳过提示，提供可随时查看的规则说明。
3. 根据试玩测量调整前期棋盘、地雷密度、起始资金、价格、扫雷目标、机器人速度、采矿附加分与时间加分系数；检查玩家是否有资金做不止一种有效投资、机器人是否能持续推进棋盘、玩家是否看得出闲置原因，以及到点结算和重试是否容易理解；核查盘面是否经常迫使玩家猜雷。
4. 将局内资金、扫雷通关进度与结算积分明确分开，并将“本局结束”与“关卡达标”分开处理：提前达到扫雷目标时结算采矿及剩余时间附加分并解锁下一关；90 秒到点时结束指挥、结算并保留已有收益，未达标则显示重玩入口且不解锁下一关。在 HUD 与结算页清楚区分“当前资金”“扫雷目标”“当前积分”“采矿附加分”“时间加分”，改造当前 `timeout` 判负、无收益结算、统计连胜和快通关加星逻辑；每日挑战等其他模式的规则另行核对。

**完成标准**：有扫雷经验的玩家无需口头解释，就能在第一关亲手购买机器人并看到它们推进棋盘、采矿增加附加分，明白购买不扣积分；在后续关卡自主作出至少一次有可见效果的运营调整。较慢达标得分较低，较快达标能在结算页看见更高的时间奖励；90 秒到点正常结算已有收益，未达标可重玩且下一关仍锁定。

### 第 5 步：制作发行候选包

**要做**

1. 补关键动作的声音和必要反馈，校对数字、旗子、矿脉与机器人状态的可读性；让设置面板只呈现真实生效的选项。
2. 在窗口、全屏及常见 16:9 分辨率检查布局和鼠标操作。
3. 随包加入玩家操作说明、版本号、存档位置、已知限制、反馈方式、Godot 与字体等授权声明；核实所有实际交付素材的来源和使用权限。
4. 在干净 Windows 环境完整走一遍首次启动、关卡、胜负、重试、退出重进、设置与清档。

**完成标准**：候选压缩包可直接交给外部玩家，且包内没有调试入口、过程文件或缺失资源。

### 第 6 步：封闭盲玩与迭代

**要做**

1. 邀请 5–10 位有一定扫雷经验、但没参与本项目开发的人，不口头教学，观察启动、首关、解锁、产业链与结算的实际过程。
2. 记录卡点、首关完成情况、首次机器人开格/标雷和首次采矿得分的时间、机器人与玩家各自完成的扫雷操作比例、耗时、错误日志、误操作、被迫猜雷感受；重点观察玩家是否把机器人扫雷视为主玩法、采矿是否分散注意力、如何分配有限资金、是否主动调整投资与布局，以及调整后能否感到扫雷速度变化；集中修复阻塞与普遍误解。
3. 从确定的提交再次构建、复测并标记 v0.1；依据结果决定是否扩大测试人群。

**完成标准**：所有测试者都能启动；无已知崩溃或进度阻塞；多数测试者能独立完成首关。未达标时继续迭代本步骤。

## 公开 Demo 阶段

封闭试玩的反馈稳定后，继续打磨内容、画面、声音与节奏，再准备商店页、截图、宣传片及平台发布。原有 [`M1 开发主线`](M1-可宣传里程碑-开发主线.md)与 [`todo.md`](../../todo.md)中的相关任务在此阶段重新核对，避免按旧勾选状态判断当前进度。

- [Factorio 开发日志 #327](https://www.factorio.com/blog/post/fff-327)讨论手动操作到自动生产、再到自动物流的渐进体验；[开发日志 #284](https://www.factorio.com/blog/post/fff-284)讨论自动化需要明确目的与资源压力。**对本项目的推断**：用短暂的手动扫雷建立需求，再让机器人接管重复劳动，并以资金、产出和运输反馈支撑运营决策。
